# Spec screenshots

The images in `docs/spec/img/` are generated by the scripts in this folder. They are never edited by hand: no cropping, no arrows, no retouching. One state hides a part of the page with a style, and its comment in `capture.mjs` says why: `settings-desktop-top` hides the native file input that the old build means to hide but does not. To change an image, change its state in `capture.mjs` (or the data in `seed.mjs`) and capture again. A screenshot that no longer matches its page is a bug in one of the two.

| File | Job |
| --- | --- |
| `seed.mjs` | Fills a fresh instance with the accounts and messages the images show. |
| `capture.mjs` | The list of named states. Drives the page into each state and writes the PNG. |
| `common.mjs` | Shared parts: arguments, devices, database lookups, sign-in, which app is the target, waits. |

## What you need

- Node 22 (the scripts use `node:sqlite` to read login tokens; no other database tool).
- Playwright with Chromium. The repository root pins it: `npm ci --ignore-scripts --no-audit --no-fund`, then `node node_modules/playwright/cli.js install chromium`. To use another install, set `PLAYWRIGHT_MODULE=/absolute/path/to/playwright`, as for the browser tests.
- The .NET SDK that builds the app.

## 1. Publish and run the app

The visual target is the page at commit `0cb67422`. Build it outside this working tree: the tree is also built from Windows, and mixed-OS `bin/` and `obj/` folders break its styles.

```sh
WORK=/tmp/yap-spec                       # any folder outside the repository
mkdir -p "$WORK/src"
git -C /path/to/Yap archive 0cb67422 | tar -x -C "$WORK/src"
dotnet publish "$WORK/src/Yap/Yap.csproj" -c Release -o "$WORK/app"

cd "$WORK/app"
ASPNETCORE_ENVIRONMENT=Development dotnet Yap.dll --urls http://127.0.0.1:7651
```

`ASPNETCORE_ENVIRONMENT=Development` is necessary. Without it the static files fail and the page never starts.

The app keeps its data inside `$WORK/app`: the database and settings in `Data/` (the database is `Data/yap.db`), uploaded files in `wwwroot/uploads/`. For a fresh start, stop the app, delete `Data/yap.db*` and `wwwroot/uploads/*`, and start it again.

Stop the app by its process ID (`kill <pid>`). Do not use `pkill -f`: a pattern that matches `dotnet Yap.dll` also matches the shell that runs the command.

### The current client

Two states need the current client (`wwwroot/chat-client`), because the old page has no New messages pill and no offline pending rows: `timeline-desktop-pill` and `offline-phone-pending`. Publish the current commit the same way, in its own folder and on its own port:

```sh
mkdir -p "$WORK/main-src"
git -C /path/to/Yap archive HEAD | tar -x -C "$WORK/main-src"
dotnet publish "$WORK/main-src/Yap/Yap.csproj" -c Release -o "$WORK/main-app"

cd "$WORK/main-app"
ASPNETCORE_ENVIRONMENT=Development dotnet Yap.dll --urls http://127.0.0.1:7652
```

The scripts find out which app an origin serves: only the current client answers `/chat-client/app.js`.

## 2. Seed

```sh
node docs/spec/tools/screenshots/seed.mjs --origin http://127.0.0.1:7651 --db "$WORK/app/Data/yap.db"
node docs/spec/tools/screenshots/seed.mjs --origin http://127.0.0.1:7652 --db "$WORK/main-app/Data/yap.db"
```

On the current client the seed runs only the base below (its two states need only the lobby) and takes about ten seconds. The current client sends no welcome message once the bot conversation exists, so there the seed does not wait for it.

On a fresh instance, registration is open, so a new name at `/auth/signin?username=<name>` creates the account. The seed creates `alice` and `bob` that way and then uses the real page, like a user, to write:

- about 30 messages between them in `#lobby`, with a few emoji, one image, one reply and one reaction;
- a direct message thread of six messages.

It then waits with the bot conversation open until the bot's welcome message arrives (the bot sends it one minute after sign-up). That keeps unread badges out of the images.

After that come the additions:

- the direct thread grows by six steps: a group of three rows from `alice` between two rows from `bob`, then a GIF from `alice`;
- two of alice's emoji in that group are picks in the emoji picker, not typed, because only picks and reactions fill the account's recent emoji;
- the GIF is a small animated GIF that the seed draws itself, uploaded with the GIF picker's upload button; the upload also makes it alice's favourite;
- three reactions on bob's reply in `#lobby`: bob 👍, alice 😂, bob 😂. For alice only the second pill is her own;
- two generated photos in one message from alice in the direct thread, for the gallery viewer's counter (the lobby keeps its last rows).

Then the data of the frame, presence and notification images:

- two more accounts, `carol` and `dave`;
- two rooms that alice (the admin) makes with Add Room: `general`, with a two-line description, and `random`;
- bob's profile, set on his Settings page: display name "Bob K.", a bio, the location "Brno";
- messages alice has not read: two from bob in `general`, one from bob in `random`, two direct messages from carol, one from dave;
- alice's notification settings: rooms and direct messages in Individual mode, `#lobby` and `#general` allowed, `#random` and dave muted. So the sidebar shows a count on `general` and carol, a crossed bell and a dot on `random` and dave, and the mailbox shows 4;
- last, alice opens the bot conversation (the bot tells the admin "just joined" for each first session), and dave signs out, so he shows offline.

Before the unread messages arrive, alice opens each new direct message once. The old page saves a count only on the reader's existing read row and never makes one, so without that visit the count is gone after a restart.

The seed takes about one and a half minutes.

The base seed runs once: if `alice` or `bob` already exists, it skips it. The additions run every time and skip each step that is already there, so an instance seeded before they existed gets them, and a second run adds nothing.

### The bot's admin flag (old page)

The old page makes the bot the first account, so the bot is created as the admin. It then takes the flag back only in memory, and after each restart the bot is an admin again: the Users table on Admin shows its crown. Clear the flag in the database while the app is stopped, then start the app again:

```sh
node -e "new (require('node:sqlite').DatabaseSync)(process.argv[1]).prepare(\"UPDATE Users SET IsAdmin = 0 WHERE Username = 'ping'\").run()" "$WORK/app/Data/yap.db"
```

This is the one write that does not go through the page. Do it once after the seed; a restart keeps it. `admin-desktop-users` stops when a row other than alice's has the crown.

## 3. Capture

```sh
node docs/spec/tools/screenshots/capture.mjs --origin http://127.0.0.1:7651 --db "$WORK/app/Data/yap.db"
node docs/spec/tools/screenshots/capture.mjs --origin http://127.0.0.1:7651 --db "$WORK/app/Data/yap.db" input-box-phone-sheet
```

```sh
node docs/spec/tools/screenshots/capture.mjs --origin http://127.0.0.1:7652 --db "$WORK/main-app/Data/yap.db"
```

With no names, every state of the app at `--origin` is captured. A named state that needs the other app stops the run with a message. A state name is `<page>-<device>-<state>` and is also the file name in `docs/spec/img/`. The script signs in with the account's token from the database (`/auth/refresh-token?token=...`), so it creates no accounts. The data it changes, it changes back, with one exception: on the old page, each first session of bob or carol makes the bot write alice a "just joined" note, which alice then reads.

`--origin` and `--db` can also come from `YAP_ORIGIN` and `YAP_DB`.

Devices: `desktop` is 1280 × 800. `phone` is 390 × 844 with touch, at device scale factor 2. `settings-desktop-top` uses a desktop window 1400 px tall: the page from the header to the end of the Appearance card is about 1370 px, and the page scrolls inside its own column, which a full-page shot does not reach. All captures use the light theme ("Daylight"), set with the page's own theme switch. The app's default theme is dark. The current client applies the account's theme again with every server update that carries it, so its states switch again after such an update.

The phone profile sends Chromium's desktop User-Agent. The old page decides on the server, from the User-Agent, whether a device is a phone, so `frame-phone-sidebar` sends a phone's: only then does the sidebar show the info buttons.

A desktop input box image is the conversation column from about 260 px above the bottom of the window. The top edge moves up to the gap above a message row, so no row is cut. A desktop message row image is the conversation column from 12 px above its first row to 12 px below its last. A desktop picker image is the picker and the input box with 12 px around them.

While it captures, the script keeps one more session of `alice` open. When the last session of a user closes, the server sets the user Away, and the header of the next whole-screen image would show it. A whole-screen state fails when the header does not show alice as Online.

The old page keeps a lost session for four hours, as Away, and a new session of the same person does not reset that. So on the old page the extra session of alice picks Online in the status menu. The states that show the people list or the status pills on Admin (`frame-desktop-room`, `frame-desktop-profile-card`, `frame-phone-sidebar`, `presence-desktop-list`, `notifications-desktop-sidebar`, `settings-desktop-top`, `admin-desktop-users`) also need other people online: for them the script opens a session of bob, who picks Online, and of carol, who picks Away. dave must have no session at all, or his dot is orange. The seed signs him out for that reason. If dave has a session anyway (for example from an older seed), the run stops: restart the app, which forgets every session. The unread counts survive the restart.

## Adding a state

Add an entry to `STATES` in `capture.mjs`: the page prefix, the device, a state name and an async `drive(page)` function. `drive` brings the page into the state and returns the clip rectangle, or `null` for the whole screen. Make `drive` fail when the page is not in the state the image claims to show (see `expectWidth`), so a changed page does not silently produce a wrong image.

Optional fields: `app: 'main'` for a state of the current client; `people: true` when the image shows the people list; `signedOut: true` for a page without a signed-in user (no status check); `noHeader: true` for a whole-screen page outside the chat frame, such as Admin (no header, so no status check); `userAgent` to send another User-Agent. In `drive`, `page.openAs(user, path)` opens another person's session for this state only, and a function in `page.cleanup` runs after the screenshot, to undo a change the state made.

## Differences between two captures

Some parts change from one capture to the next. This is expected:

- The room placeholder, the emoji toggle's emoji, the room title in the header and the title of the people section are picked at random by the server each time the page opens. The text of the New messages pill is picked at random too.
- A GIF shows whichever frame is current.
- Message times are the times of the seed run.
