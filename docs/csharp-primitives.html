The C# primitives that carry a chat message

A text message enters Yap as an HTTP POST and leaves as an item on a SignalR stream. On the way it crosses a keyed SemaphoreSlim, one global async mutex, a SQLite transaction, a per-conversation lock, a synchronous event, a bounded queue with a one-slot Channel<bool> doorbell and an IAsyncEnumerable.

Scope the server, about 20k lines of C# without migrations Line numbers refer to the commit above and will drift Method every claim comes from the source. Items not confirmed at runtime say unverified Excerpts drop namespace prefixes and reflow a few lines
Every write is an HTTP request. The hub never accepts a message. The server pushes only through two server-to-client streams. Nothing in the fan-out owns a thread: projection runs on the sender's request thread inside the conversation lock, and the only background loop in the live path is a 100 ms presence ticker.
Chapter 1

The shape after the rewrite

The rewrite replaced the Blazor Server chat page with a JS PWA in wwwroot/chat-client. The server kept ChatService as the domain core and added HTTP and SignalR adapters in the layer folders: Endpoints/Chat*.cs, Hubs/ChatHub.cs, Services/ChatProjection.cs, ChatChangeTracker.cs, ChatFanout.cs, PresenceService.cs, and the wire records in Contracts/. The old event bus still exists but now serves only the Blazor pages that remain (Login, Settings, Admin) and the system bot. The new push path is a separate chain: change signal, fan-out, per-connection queue, hub stream.

flowWhat the hub does and does not do

Two server-to-client streams: WatchChanges (deltas) and WatchActivity (presence and typing). Three client-to-server calls: Report, Typing, SetStatus. There is no Clients.*.SendAsync, no IHubContext, no Groups, no OnConnectedAsync, no hub options. SignalR runs on defaults with the JSON protocol.

Chapter 4

Flow: channels and streams

Only two places in the server create a System.Threading.Channels channel, and both channels hold one item. Neither carries the payload. One is a doorbell for a locked queue, the other is a latest-value mailbox. The payload itself travels on IAsyncEnumerable yields that SignalR turns into stream frames.

The per-connection queue

Why not a Channel<ChatUpdate>?

Three operations need to be atomic and a channel offers none of them. Overflow must clear the queue and set a flag together. Read must drain everything and reset the flag together. And the merge step needs the whole batch at once, because entries for one conversation collapse into a single patch. A Queue<T> under a lock gives all three in a few lines. The code comment does not state this reason. It is my reading of the shape.

Why a one-slot Channel<bool> as the doorbell?

It is the cheapest awaitable signal in the BCL. TryWrite on a full Wait-mode channel returns false without blocking, so a hundred enqueues produce one wake-up. TryRead under the gate after the drain discards a stale wake-up. The default AllowSynchronousContinuations = false means the reader's continuation never runs on the publisher's thread, which still holds two locks at that moment.

The hub stream that drives it

  • Identity. CurrentUser() re-authenticates from the cookie on the connection's HttpContext on every batch and every hub call. The code never uses Context.User, UserIdentifier or Groups. The subscription is keyed by its own Guid. Presence is keyed by "chat:" + ConnectionId.
  • Teardown. SignalR cancels the token when the client drops. ReadAsync or Task.Delay throws, using disposes the subscription (clear queue, TryComplete the doorbell, remove from the three indexes), the finally block unsubscribes the kick handler.
  • Slow client. SignalR awaits each item write. While a write waits, the loop does not call Read, the queue fills to 128, then overflows into a Reset. Memory per slow connection is bounded by construction.
  • Hub lifetime. The Hub instance is transient per invocation. Per-connection state lives in Context.Items, which is why the token bucket and the one-stream flag lock that dictionary rather than a field.

The presence mailbox

Presence and typing do not ride the change stream. They are polled from ChatService by a 100 ms ticker, projected once per tick, and pushed through a second one-slot channel per connection. The channel is DropOldest, so it always holds the newest view and never blocks the ticker.

  • Cheap change test. Tick replaces the people array only when its content changed, so the per-listener dedupe can use ReferenceEquals(previous.View.Users, view.Users) instead of comparing arrays.
  • Typing keepalive. While someone types, the same view is re-sent once per second even if nothing changed, so the client's typing timeout can be a plain timer.
  • Rate. At most ten views per second per connection, by construction of the ticker. The ticker runs with or without listeners.
Chapter 5

Signalling: the old bus and the new one

ChatService declares fifteen Action events. Before the rewrite, Blazor components re-rendered on them. The rewrite did not remove that bus. It added a second, narrower one: a single event Action<OfflineChange> with one subscriber. Every committed write calls Touch on it. The old events are raised a line later and reach only Blazor pages, the bot and the tests.

Two overloads, two meanings

The channel overload bumps versions and must run under the conversation lock so the version it reports matches the memory state the fan-out will project. The kind overload (Unread, Profile, People, Media, Gif, Favorites, Settings, Preferences) only stamps a sequence. It must not advance a conversation revision or leak a private channel id.

The history flag

An arrival passes history: false, so cached older pages on the client stay valid. An edit, delete or reaction uses the default true and invalidates them. The README states the rule: history versions invalidate older cached pages on mutations while allowing ordinary arrivals to preserve them.

Synchronous on purpose

Publish runs each subscriber inline with its own try/catch. There is no queue here and no backpressure. The queue is one hop later, per connection. The cost of that choice is that the sender's thread does the projection. The benefit is that projection sees exactly the state the version bump describes.

Chapter 6

Coordination: locks and gates

The codebase uses a lock where the critical section is synchronous and short, and a SemaphoreSlim(1,1) where it must await. C# forbids an await inside a lock, so the compiler enforces the split. The one place that needs a mutex per key builds it by hand with a reference count.

Keys in use: operation:{userId}:{operationId} for sends and mutations, message:{messageId} nested inside it for mutations, and dm:{min}:{max} for DM creation. Callers write using (await LockAcceptance(…)), so release is a disposal and therefore effectively a finally block.

The nesting order is the operation gate, then the message gate (mutations only), then readStateGate, then the conversation lock, then Subscription.gate. The fan-out never takes them in reverse, and a comment says so at the line where it would be tempting. I found no nesting between _connectionGate and a conversation lock.

A rejected Report, SetStatus or Typing returns Task.CompletedTask. The client sees success and nothing happens. Join is not limited.

Lock-free where it is safe to be wrong. CircuitTracker updates its records with a read-modify-write and no lock, and documents why: all frequent writers for one circuit run on that circuit's own dispatcher, and a dropped telemetry sample is harmless. That is a deliberate trade, written at the line where someone would otherwise add a lock.
Chapter 7

Collections

ConcurrentDictionary is the default map everywhere a singleton is read from many contexts. It buys lock-free reads. It does not buy compound atomicity, so every multi-step write still takes a gate, and the inner values are mostly plain List and Dictionary instances guarded by the conversation lock. The reason is written where the GIF and author indexes are declared.

One-shot timers with an injected clock

The disconnect lifecycle uses the same idiom twice over: a one-shot timer after the 30 s grace runs the auto-away check and then re-arms itself with Change(remaining, Infinite) for the rest of the 4 h retention, when it removes the session. Every CreateTimer call sits inside a _connectionGate section and every callback takes the gate first, so pending.Timer! is always assigned before a callback can read it.

Chapter 10

Catch-up and versions

Everything that orders the wire is an in-memory counter. That is why the protocol carries an epoch: after a restart every counter is zero again, and the client must not compare revisions across epochs. There is no content hashing and no second message database. Every snapshot is rebuilt from ChatService memory under the conversation lock.

Epoch
A new Guid per process (ChatChangeTracker.Epoch). A mismatch marks every cached window stale on the client.
Sequence
One Interlocked counter for the whole process, stamped on every packet. The client orders HTTP acknowledgements against stream items with it. The ack is captured after the lock, so its stamp is higher than the stream item for the same message.
ContentVersion
Per channel, bumped by every arrival and mutation. Sent as the string revision. A delta carries baseRevision = before and revision = after. The client applies it only on top of baseRevision, otherwise it marks the window unloaded and refetches.
HistoryVersion
Per channel, bumped by mutations only. A change invalidates the client's cached older pages. An arrival does not.
Invalidate
A metadata-only patch that tells the client to refetch the window with GET /api/chat/windows/{id}.
Reset
A packet that replaces the complete allowed set. Sent by bootstrap and by overflow recovery.

Bootstrap skips unchanged bodies

GET /api/chat/bootstrap takes the client's epoch, revision and known user. When all three match the selected conversation, the response carries metadata only. Chapter 12

Vocabulary

operationId
Client-generated Guid per send or mutation. The idempotency key. Bound to a content hash in the receipt.
receipt
TextSendReceipt: (user, operationId) → message id, channel, hash. Independent of messages and channels so a delete never makes an accepted operation reusable.
acceptance
The point where a write is stored and becomes authoritative. "Store first, publish memory second." Notification failures after it are logged, never retried.
conversation lock
The per-channel Monitor object from ChatChangeTracker.ChannelLock. Guards the list, the counters and projection order.
Touch
The one publication call. The channel overload bumps versions under the lock. The kind overload only stamps.
projection
Turning a live ChatMessage into a MessageView DTO. Done once per event, then adjusted per viewer by ForViewer.
window
The recent-message slice of one conversation that the client caches. Replaced whole when invalidated.
digest
The 10 s pass on every change stream that repairs dropped revisions and revalidates the cookie.
ticket
A two-minute ITimeLimitedDataProtector token from bootstrap, consumed by Join. Ties a hub connection to the account that bootstrapped.
session key
"chat:" + ConnectionId for hub sessions. The same literal appears in three places. A kick or a close matches on it.
foreground reader
A visible session that reported within 35 s, whose user is not Away, and whose unread count for the channel is zero. Exempt from the unread increment.
compact authority
The update field on every write response: current metadata plus the one message, captured under the lock, so the client can reconcile without waiting for the stream.
