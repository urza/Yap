How a chat message moves in Yap

This page shows the chat path only. It covers the JS client in wwwroot/chat-client and the .NET code that serves it. It does not cover Login, Settings, Admin or Blazor.

Two connections

  • HTTP requests to /api/chat. The browser uses them to send messages and to get conversations.
  • One SignalR connection to /hubs/chat. SignalR is the ASP.NET Core library that keeps a connection open between the browser and the server. The server class for this connection is the hub, OfflineHub. The hub sends changes to the browser as streams. A stream is a series of items that the server sends one by one on the open connection.

Main rules

  • The browser sends each new message as an HTTP POST. It does not send messages through the hub.
  • The server sends each change to the browser as an item on a hub stream.
  • The browser keeps a copy of the chat in IndexedDB, a database inside the browser. Thus it can show the chat and queue messages with no network.
  • The server keeps all messages in memory. SQLite stores each accepted write. In no-database mode, memory replaces SQLite.

Words on this page

outbox
A store in IndexedDB. It holds the messages that the server did not accept yet. Each row is one message.
operationId
A random id that the browser gives to each outbox row. The server uses it to accept each message only one time.
receipt
A server record of an accepted operationId. It holds the id of the message that the server made.
update
One packet from the server, type ChatUpdate. It has a sequence number and changes for one or more conversations.
patch
The part of an update for one conversation, type ConversationUpdate. It can hold new messages, removed message ids and new conversation data.
revision
A version number of a conversation. It increases by one at each change. The browser compares revisions to find a missed patch.
window
The recent messages of one conversation that the browser keeps. It holds up to 100 messages.
epoch
A new id each time the server starts. The revisions start again after a restart, so the browser does not compare them with old revisions.
fan-out
OfflineFanout. It sends one change to each connection that can read the conversation.
DTO
The message object that the server sends to the browser, type ReaderMessage. It does not include passwords or database fields.

2. Open the chat

The page shows the cached chat first. Then it asks the server for the current state and opens the two streams.

  • Bootstrap returns all conversations. Only the open conversation comes with its messages.
  • If the cached revision of the open conversation is current, the server leaves out its messages. The browser sends the revision, the server epoch and the user id for this check.
  • The other conversations come without messages. windows.js fetches them one at a time. It fetches the open conversation first, then the conversations with the most unread messages.
  • The first item on WatchChanges holds the current state of all conversations. The page does not show notifications for it.

3. Send a message

The page does not send a message to the server. It writes the message to the outbox in IndexedDB. The sender takes the row from the outbox and sends it.

  • The browser makes the operationId with crypto.randomUUID(). The server uses it to accept each message only one time.
  • The sender gets its own message two times: in the POST reply and on its own stream. The first copy deletes the outbox row. The second copy changes nothing.
  • If the POST reply is lost, the sender sends the same row again. The server finds the receipt and returns the same messageId.
  • If two or more text rows wait in one conversation, the sender sends them in one POST /api/chat/operations. A batch has a maximum of 16 rows and 48 KiB.
  • The sender works on a maximum of 3 conversations at the same time. The rows of one conversation go out in order.

4. Receive a message

Step 11 of the send calls Touch. From there, the server puts a patch in the queue of each connection that can read the conversation. This includes the other tabs of the sender.

  • The fan-out runs on the request thread of the sender. It does not have its own thread.
  • The fan-out builds the message DTO one time. Then it adds the flags of each viewer, for example the favorite GIFs.
  • The queue separates the two threads. The request thread does not wait for a slow browser.

5. When a send fails

Each outbox row has a status. The sender changes the status after each attempt. The status is saved in IndexedDB, so a reload or another tab continues from the same point.

  • The server keeps a receipt for 1 day. It keeps the newest 4096 receipts per user. After that, a retry of the same row makes a second message.
  • A 401 reply does not fail the row. The page locks the local data and opens the login page. The row stays in the outbox.

6. Lost connection

The browser does not use the automatic reconnect of SignalR. It makes a new bootstrap request and a new hub connection.

The server sends repair data in four cases. In each case the browser fetches only the conversations whose revision changed.

7. Presence and typing

Presence and typing do not use the outbox or the change stream. The browser sends them as hub calls. The server collects them and sends a view every 100 ms when the view changes.

  • send does not wait for a reply. SetStatus uses invoke and waits.
  • The hub limits Report, Typing and SetStatus to 12 calls at once and then 4 calls per second. A call above the limit does nothing and returns no error.
  • The channel per connection holds one view. A new view replaces a view that the stream did not send yet.

9. Browser storage and tabs

Each tab has its own hub connection and its own two streams. The tabs share one IndexedDB database. Locks make sure that only one tab writes or sends at a time.
