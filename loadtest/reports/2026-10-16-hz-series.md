# Load test report: hz.urza.cc, 2026-10-16

Purpose: find the limits of the current design. No code changes follow from this report.

## Test machine

Hetzner Cloud VPS in Helsinki (hel1). The specs match the CCX23 plan (4 dedicated vCPU, 16 GB,
160 GB); the plan name is from the specs, not confirmed in the console.

## Why 2000 users in one room saturate four cores

Every action in a room costs one hub send per connected member, so the work grows with the square
of the room size.

| Action | Sends per action with 2000 members | Source |
|---|---|---|
| A message | 2000 `message` events | `ChatHubBroadcaster.ToChannel` |
| The unread count for the same message | 2000 `unread` events + 2000 read-state updates (DB writes when persistence is on) | `ChatService.IncrementUnread`, counts every connected user and every account with the room unmuted, including people who have the room open |
| Typing before the message | 2000 `typing on` + 2000 `typing off` | `PresenceService.SetTyping` |
| A presence change | 2000 `presence` events | `PresenceService.Changes.Raise`, one event per change, to everyone |

Rates in this preset at 2000 users:

- About 100 visible users with a 60 s mean think time give about 2 messages/s.
- 1900 hidden users each come back about once in 10 minutes, about 3 presence changes/s.
- 2 messages/s × 8000 sends + 3 changes/s × 2000 sends ≈ 20,000 hub sends/s.
- At about 1 KB per frame that is the observed 15 to 20 MB/s outbound.
- At about 150 µs of CPU per send that is about three cores, which matches the Yap CPU.

## Limits of the current design, as measured

- Connections alone are cheap: 500 idle sockets with heartbeats cost about 5 % of one core and
  about 0.1 MB of RSS per connection.
- One room is the unit that scales badly. A room of 2000 connected members saturates a 4-core box
  with two messages a second and no media.
- The same 2000 users spread over 20 rooms of 100 would cost about 1/20 of the sends per message.
  The `small-rooms` preset measures that.
- The knee lies between 1000 and 2000 members in one room on this box. A finer run with
  `--steps 1000,1250,1500,1750` would place it exactly.

## Where the cost sits, for a later decision

Not changed now. Recorded so the numbers above can be read against the code.

1. Unread fan-out to viewers: people with the room open get an `unread` event and a read-state
   write for each message they are watching. In a big room that is almost all of the unread
   traffic.
2. Typing events to every viewer of a large room, twice per message.
3. One presence event per change to every connection, with no batching.

### Why the writer falls behind

Three messages a second with 1000 members queue about 3000 read-state writes a second. The
writer (`PersistenceWriter.RunAsync`) drains the whole queue in one transaction, but each write
runs `FindAsync`, `SetValues` and its own `SaveChangesAsync` on one shared `DbContext`.
`SaveChanges` runs `DetectChanges` over every entity the context tracks, and the context tracks
every row touched so far in the batch. The cost of a batch of N writes is therefore about N²
property compares. A bigger backlog makes a bigger batch, a bigger batch makes each write slower,
and the backlog grows further. That is the runaway seen in the writer depth.

Confirmed on the VPS after the run, with no users connected: Yap still used a full core, and the
database command rate per minute fell from about 14,000 to 200 over ten minutes while that one
batch kept running. Nothing commits until the whole batch ends, so the database stood still at
17:26:30, the moment the batch was picked up. A write arriving meanwhile waits for the next
batch, which starts with the same problem.

On top of the writer's own cost, EF Core logged every SQL command at information level to
journald on this instance: 114,000 lines in 12 minutes. The logging level for
`Microsoft.EntityFrameworkCore.Database.Command` is a deployment setting and part of the CPU
seen in run 2.

The queue is unbounded (`Channel.CreateUnbounded` in `PersistenceWriter`, with the comment "a
chat this size never outruns SQLite"). Consequences at this scale:

- The working set grows with the backlog (481 MB here, 287 MB at 500 users).
- Unread counts reach the database minutes late. In memory they are right, so the clients see
  correct numbers; a restart loses whatever the host shutdown timeout does not flush. After run 2
  the data on disk was more than six minutes behind memory.
- The sweep time of 272 ms at 1000 sessions comes from CPU contention, not from the sweep itself.

### What a real browser saw at the 1000 step

The admin's own tab, open in the lobby next to the load:

- Navigation is laggy: opening a DM or the settings page takes noticeably long. Each is an HTTP
  request that competes with the hub work for CPU and adds an action-log row to the writer queue.
- The typing indicator is busy all the time; the test users type like crazy.
- Own messages post after a few seconds. The page stays usable.
- The browser receives every event of the room: thousands of `typing`, `unread` and `presence`
  events a second at this size. Part of the lag is the client processing that stream, so a real
  user on a weak device feels a 1000-member room before the server does.

### Limits with persistence on, as measured

- A room of 1000 connected members at 3 messages a second is past the knee. The writer never
  returns to zero between messages.
- The knee is below 1000 members in one room on this box. A finer run with
  `--steps 200,400,600,800` would show the member count where the depth still returns to zero
  between messages.
- Connections and heartbeats alone are not the issue with persistence on either; the 500 ramp
  looked like run 1.

## Possible fixes, not applied

Collected for a later decision. None of these are in the code; this series measures the design as
it is.

Writer (`PersistenceWriter`):

1. `db.ChangeTracker.Clear()` after each `SaveChangesAsync()` in the batch loop. Turns the cost of
   a batch from N² into N. The main fix.
2. A fixed batch size, for example 500 writes per transaction, so one commit never waits on
   minutes of work and the disk is never far behind memory.
3. Coalesce read-state writes inside a batch: the same (user, room) row is upserted once per
   message, and only the last value matters. One write per row per batch instead of one per
   message cuts the unread writes in a busy room by the message count of the batch.
4. A bound on the queue, or at least a warning in the log when the depth passes a threshold, so a
   runaway shows up before the working set does.

Deployment:

5. `Logging:LogLevel:Microsoft.EntityFrameworkCore.Database.Command` = `Warning` in Production.
   Every SQL command at information level is one journald line per write.

Fan-out (the N² of a big room, run 1):

6. No `unread` event and no read-state write for a person who has the room open; they are reading
   it. In a big room that removes almost all unread traffic.
7. Typing events only below a room-size threshold, or coalesced to one event per second per room.
8. Presence changes collected for about 500 ms and sent as one `presence` event with a list.

### The room size does not bound the cost of a message

Two paths ignore room membership:

- The `unread` event goes to every connected user, whatever room they are in. 501 sends per
  message at 500 connected users with rooms of 25 is exactly that: 25 `message` sends plus 475
  `unread` sends.
- The read-state write goes to every account that has the room unmuted, which is every account
  on the server (`ChatService.IncrementUnread`: connected users, then all users not muted for the
  channel). 1500 accounts × 7 messages/s ≈ 10,000 writes a second, and the writer runs away at
  half the user count of run 2.

Seen on the VPS during the 500 step: nothing committed after 17:49:34, the writer ran one
transaction at about 250 database commands a second while about 10,000 writes a second arrived.
Yap used about 2.2 cores and the box 63 %, so the CPU had room; the writer was the limit on its
own, before the fan-out was.

previews stay on at scale.

users, not with the size of the room. Twenty rooms of 25 cost the same unread work as one room of
500. The only savings of small rooms are the `message` and `typing` sends.

### The writer limit across all persistence-on runs

The VPS log for run 6: the database stopped committing at 18:00:30, about when the 800 step
reached its plateau. Writer rate per minute 13,000 to 15,000 → 8,901 → 238. The same shape in
every persistence-on run.

The writer's input is messages per second × accounts with the room unmuted (all 1500 here),
whatever the room size or the connection count. Put the steps side by side:

| Run, step | Msg/s | Writes/s arriving (× 1500) | Writer |
|---|---|---|---|
| idle-crowd 500 | 0.6 | ~900 | kept up, depth max 1,007 |
| big-room 200 | 2.5 | ~3,750 | kept up, depth max 406 |
| big-room 400 (23 s) | 3.1 | ~4,650 | kept up, depth max 330 |
| idle-crowd 1000 | 4.0 | ~6,000 | lost |

The writer on this box sustains about 4,000 to 5,000 read-state writes a second as it is written
today. With 1500 accounts that is 3 messages a second across the whole server, in any room
layout. Once it is over, the N² batch makes it fail completely instead of lagging.

## Run 10: all six presets at once, persistence off

Six orchestrators from six terminals, each with its own account prefix and state: big-room 400,
small-rooms 400, dm-heavy 400, media-heavy 200, burst 300, idle-crowd 500; 2,200 users in
total, ramp 60 s, hold 3 min. Yap restarted with persistence off, so the instance started empty
and the admin signed in first. Folders `results/20261016-2043*` and `20261016-2044*`.

Timeline from the orchestrators' server samples:

| Time | Connected | CPU % | Msg/s | Hub sends/s | Req/s served | Req p95 | Pool queue | Sweep ms |
|---|---|---|---|---|---|---|---|---|
| 18:45:03 (ramp) | 1,765 | 91 | 63 | 33,900 | 22 | 755 | 3,159 | 72 |
| 18:46:16 (plateau) | 1,869 | 77 | 70 | 1,900 | 1 | 1,321 | 4,241 | 123 |
| 18:47:24 (storm) | 1,472 | 93 | 40 | 42,800 | 36 | 654 | 2,326 | 311 |

At 18:46 the thread pool queue was at 4,000 and the server got through one HTTP request a second;
hub sends fell from 34,000 to 1,900 a second because the sends themselves waited in the queue.
The admin's browser showed an empty grey shell (the bootstrap never came) and a login took more
than a minute. At 18:47 the heartbeats timed out, connections dropped (1,869 → 1,472 in a
minute), and the presence leave and join events of the reconnects pushed the hub sends to
42,800 a second: the reconnect storm.

Per orchestrator, all with send-to-appear p95 of 28 to 31 s (the top bucket), HTTP p95 of 28 to
30 s, RTT p95 of 30 to 32 s, server CPU 100 % at peak, pool queue max 4,825, sweep max 3.3 s:

3,862 errors and 3,600 reconnects in four minutes. The 502s are Caddy answering for a Yap that did
not accept the connection in time. The `http 404` entries are messages posted to a room whose
hub group the sender had lost. The server log side was not inspected during this run.

VPS: about 8,070 TCP connections at peak (half of them Caddy to Yap), CPU at or above 95 % for
164 s, Yap at 3.9 of 4 cores, 96 s of stalls with almost no outgoing traffic while more than 1,000
users were connected, 46.9 MB/s outgoing in the bursts between stalls, Yap at 864 MB peak. Seven
"Unexpected end of request content" (uploads the client cancelled during stalls), two Kestrel
warnings, no crash; the same process from 18:43:12 served the whole run and was at 0.3 % CPU
afterwards.

### Recovery

Polled from the load machine with the admin token, every 5 s, after the orchestrators stopped:

| After the load stopped | Server |
|---|---|
| 0 s | 1,784 connections, pool queue 2,279, CPU 40 % |
| 20 s | 1,385 connections, pool queue 5,832 (the disconnects arriving) |
| 30 s | 0 connections, pool queue 0 |
| 30 to 100 s | CPU 25 to 35 % with no users: queued work draining; the last stuck requests completed with 68 to 88 s latency (the admin's login among them) |
| 115 s | CPU 0 %, working set 512 MB, 1 connection (the admin) |

The server recovered on its own in about two minutes, without a restart, and the admin could
log in and post in the lobby. The design degrades badly past its CPU but does not break: nothing
leaked, no thread was stuck, the working set went back to where it was.

## UI observations at scale (not load, but seen only at this size)

- The side panel has no scrollbar when it holds twenty rooms and 1500 people. The content runs
  past the viewport. Seen during the dm-heavy run; a CSS fix for after the series.
- The client is a limit of its own. In the dm-heavy run at 800 users the server answered HTTP
  requests in 44 ms at p95 on average (93 ms worst) and the virtual users saw their messages in
  75 to 100 ms at p95, yet the admin's browser took seconds to post a message and to open a
  room. The browser renders 20 to 27 messages a second plus typing, presence and unread events
  for 800 connected and 1500 known people, and its main thread is the queue. Where the earlier
  runs had a saturated server, this run shows the browser slow on its own.
- In the burst run at 500 users (27 to 33 messages a second) the admin's own message waited
  more than a minute before it showed as accepted, and navigating rooms was impossible, while
  the server answered requests in 20 to 34 ms at p95 and the virtual users saw their messages
  in 75 ms. The likely mechanism: a browser that cannot consume the stream as fast as the server
  writes it lets the frames pile up in its connection's send buffer, and its own echo waits at
  the end of that queue. A fast consumer never sees the queue. This makes the per-connection
  stream rate, not the server, the limit for a human in a room this busy. Confirmed in part: the
  echo arrived on its own one to two minutes after the run ended, without a reload, so the
  frames were buffered and drained, not lost, and no reconnect was involved.
- The typing indicator with about a hundred people typing at once in one room (idle-crowd at
  2000, big-room at 800) is noise rather than information.

## Summary of the series

Test box: 4 cores, 16 GB, Caddy + Cloudflare in front, 1500 test accounts on the server.
Latency floor through Cloudflare: 75 to 100 ms p95 for send-to-appear at idle.

| Question | Answer |
|---|---|
| Cost of a connection | About 0.1 % of a core and 0.1 MB each. 500 idle users: 5 % of a core. Not a limit in reach. |
| Active users in one room, persistence off | 2000 saturates the box: messages still arrive (p95 750 ms) but HTTP requests take 5 to 75 s. The N² fan-out of `message` + `unread` + `typing` per member. |
| Active users in one room, persistence on | 800 at 12.5 msg/s is fine (p95 150 ms, CPU 58 %). Knee by CPU slope around 1200. The writer is lost well before that. |
| Does splitting into small rooms help | Only for `message` and `typing`. `unread` goes to every connected user and the read-state write to every account, so 1500 users in 20 rooms cost the same as 2000 in one. |
| The persistence writer | Sustains about 4,000 to 5,000 read-state writes a second. Input is msg/s × accounts, so with 1500 accounts about 3 msg/s server-wide. Past that, the one-transaction N² batch stalls and never recovers; memory grows ~300 bytes per queued write; disk falls minutes behind memory. The first and sharpest limit with persistence on. |
| Media | Not a limit at 300 users with small images. Bursty CPU, idle disk. |
| DMs | Nearly free: two sends and one write each. 800 users at 19 msg/s with half DMs: CPU 50 %, p95 100 ms, no errors. |
| Message rate of one room | 27 msg/s sustained in a room of 500 at 46 % CPU and 75 ms p95 (burst). The hub is not near its rate limit on this box. |
| Everything at once, db off | 2,200 users across six presets: collapse within a minute of the plateau (pool queue 4,000+, one HTTP request a second, 30 s latencies, 3,600 reconnects), then full recovery two minutes after the load stopped, no restart. |
| The browser | A limit of its own in a busy room: seconds to post and to navigate while the server answers in under 100 ms. |
| What a user feels first | Navigation (HTTP: open a room, DM, settings), seconds before messaging degrades. The lobby stream itself at 13 msg/s is hard to read for a human regardless of the server. |
