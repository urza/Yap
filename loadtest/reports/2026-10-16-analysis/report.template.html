CPU pressure, with memory available

Across all files, available host memory never fell below @@MIN_MEMORY@@ GiB; swap usage stayed zero. Maximum iowait was 1.8% during setup and at most 0.5% in the other captures. The evidence points to application work and queuing, rather than exhausted RAM or sustained disk wait.

The real browser failed earlier

During the burst run, synthetic send-to-appear p95 was 75 ms while the operator’s browser took over a minute to show its own message. These are different consumers. The browser observation is qualitative; profiling is needed to locate rendering, event-processing and buffering costs.

The source supports the failure mechanism

PersistenceWriter drains an unbounded queue into a batch, creates one context and transaction for that batch, and calls SaveChangesAsync after every queued operation. Tracking persists until the batch ends. A long batch delays commits and repeatedly scans tracked state.

The context is new per batch, not permanent. The scan cost depends on operations × tracked entities; quadratic growth is a possible worst case as distinct entities accumulate, not a proven law for every repeated read-state update.

PersistenceWriter.cs · Writes.cs

The practical consequence is data risk

The Markdown reports that after the DM-heavy run and restart, the database ended at 18:20:21 although the run continued to 18:23:45: 3 minutes 24 seconds missing on disk. This is the strongest reported durability consequence; host CSVs alone cannot verify database contents.

The source’s ≈4–5k writes/s “limit” is an estimate from mixed workloads and short holds. Treat it as a retest target, not a measured SQLite throughput ceiling or a production guarantee.

A flat writer-depth sample does not prove zero work: the counter decreases only after a whole batch finishes, and includes in-flight operations. Database commit timestamps are better evidence of durability lag. The report’s SQL command-rate observations are not equivalent to committed logical writes per second.

06 /

Fix the queues, then measure again.

Prioritize durable progress, then reduce global work and protect slow consumers. These are proposed changes and validation targets; no application fixes are part of this report.

P0

Bound transaction work and make durability observable

Use a capped batch or commit-time budget; address repeated change tracking; coalesce redundant read-state updates where ordering allows. Add oldest-uncommitted age, commit duration, batch size, distinct tracked entities and actual committed throughput. Benchmark tracker clearing or shorter context lifetimes with insert/edit/delete ordering intact. Define overload behavior before placing a hard bound on the queue.

Retest: repeat 1,000-user idle, 500-user small-rooms and 800-user big-room runs. Require backlog to stabilize and drain, commit age to meet an explicit durability target, and all acknowledged messages to survive a controlled restart.

P1

Reduce unread, typing and presence amplification

Avoid unnecessary unread work for people already reading, or redesign unread state around per-room message positions and per-user read cursors. Preserve offline unread, mute, visibility and multi-device semantics. Coalesce typing and presence updates; measure delivered bytes and recipients separately from send-call counts.

Retest: hold connected users and room-message rate fixed while varying total accounts and room count. That separates account-wide persistence cost from room-local fan-out.

P1

Profile the real browser and slow-client queues

Record a browser performance trace at the burst workload. Measure long tasks, event-handler time, DOM work, queued transport bytes and own-echo latency on the same client. Explore batched UI updates, a bounded rendered message list and coalescing ephemeral events; protect message delivery semantics. Fix the observed sidebar scrolling issue separately.

Retest: exercise sending, room navigation and settings in real browsers, including a slower device, while synthetic clients maintain load. Capture browser timings alongside server and worker measurements.

P2

Run a controlled capacity series

Turn SQL-command logging down to Warning for the production-like baseline; retain a logging-on comparison. Use fresh, documented account counts and full 10–15 minute holds around the threshold. Record exact effective presets, deployment commit, ramp/hold boundaries, client host load and raw client timelines. Compare direct-to-origin and proxied paths in a separate experiment.

Retest: define success jointly: latency, error/reconnect counts, bounded backlog and commit age, browser usability, and recovery time. Repeat each boundary point; do not extrapolate a user ceiling from two CPU measurements.

Interpretation

Mechanisms and capacity

Code inspection supports global unread work and batch-related durability lag. Exact bottleneck shares, future capacity, per-connection cost and browser buffer location require controlled measurements.

Metric definitions that change the reading
  • CPU denominators: host cpu_pct is a percentage of the whole box; host proc_cpu_pct uses 100% per core. Divide process CPU by four to compare with the application’s all-core CPU percentage. Initial process samples after attachment report a synthetic zero; the explorer leaves those process points blank.
  • Hub calls are not recipients: HubSendsPerSec increments once per SendCoreAsync call. A group broadcast counts once; a user-targeted call also counts once, even if no connection receives it. Do not infer frames, users reached or wire bytes by multiplying this counter by a guessed payload size.
  • Writer depth includes in-flight work: it is decremented after batch completion, not after each SQL command. Reported latency measures the memory/transport path and is not a commit acknowledgement.
  • Latency populations differ: the worker’s HTTP p95 is the message POST round trip; the server request p95 samples all logged requests. Per-step histograms, rolling-window percentiles and maxima of per-second p95s cannot be compared as if they were the same percentile. Client bucket values are upper bounds; the overflow bucket uses the observed maximum.
  • Fan-out timing: synthetic clients run on the same Windows host and carry the send timestamp in the client ID. This avoids cross-machine clock skew for that metric. Successful observed echoes do not by themselves cover timed-out or disconnected operations.
  • Environment: 4 vCPU / 16 GB, no swap, .NET 10 and SQLite on a systemd service, through Cloudflare → Caddy → Yap. The reported CCX23 plan name is inferred from specifications. The 75–100 ms floor is end-to-end observed latency; the isolated Cloudflare/Caddy contribution was not measured.
Capture coverage and inconsistencies in the source report
  • Run numbering is preserved: there is no standalone run 4 section. host-test-4-big-room.csv maps to reported run 6. Run 1 has no host CSV; host.csv is run 2 setup.
  • Restarts fall inside two files: setup loses its process at 17:19:17 and attaches PID 19492 at 17:19:18. Small-rooms loses its process at 17:56:58 and attaches PID 24039 at 17:56:59. Its final 43 samples belong to the replacement process; full-file means must not be presented as a single-process plateau.
  • Scenario descriptions are not fully reproducible: run 6 is described as everyone visible, but the committed big-room default uses 30% visibility. The burst run is described as one room, but its default creates three. No exact invocation or effective configuration is included to resolve these differences. The DM mix weight is 50 of 115 action weights, with room bursts and visibility also affecting realized traffic; “half DMs” is approximate.
  • Some source conclusions overreach: “800 is fine” applies to synthetic responsiveness, not durable operation. The suggested ≈1,200-user CPU knee is an extrapolation. The claimed 4–5k write/s capacity is approximate. A DM avoids the account-wide unread loop but still writes the message and recipient read state, plus possible other work.
  • Do not carry forward stale statements: the early prediction that 20 rooms would cut message-related work by 20× is qualified by the later global-unread finding. The final “Pending” list still names scenarios already reported. The stated per-connection CPU estimate is internally inconsistent: 5% of one core / 500 is 0.01% per connection, not 0.1%, and lacks a clean baseline subtraction.
  • No precise plateau join: the host CSVs contain no run-step boundaries and the raw client timelines are absent. This report aligns only the explicitly stated UTC checkpoints; it does not invent per-step host statistics.
