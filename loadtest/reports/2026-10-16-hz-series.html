How much Yap handles on a 4-core box, and what gives first

Ten runs with synthetic users against a test instance, with persistence off and on. The report records what the current design does at each size and why. No code was changed because of these results.

10runs, 6 traffic shapes
2,200users at once in the last run
800active users in one room: fine
~4,500writes/s before the database writer stalls
2 minto recover after a full collapse, no restart

Findings

  • Connections are cheap. 500 idle users with heartbeats cost 5 % of one core and about 0.1 MB each.
  • One active room of 800 is fine. 12.5 messages a second, p95 send-to-appear 150 ms, CPU 58 %. The CPU slope points at a knee around 1,200 for one room.
  • 2,000 in one room saturate the box. Messages still arrive (p95 750 ms) but HTTP requests take 5 to 75 seconds. Each message costs one send per member for the message, one per member for the unread count, and two per member for typing.
  • Small rooms do not help the two expensive paths. The unread event goes to every connected user and the read-state write to every account, whatever room the message is in. 1,500 users in twenty rooms cost the same as 2,000 in one.
  • With persistence on, the database writer is the first limit. It sustains about 4,000 to 5,000 read-state writes a second. One room message writes one row per account, so with 1,500 accounts that is 3 messages a second across the whole server. Past that, the writer stalls for good until a restart, and the disk falls minutes behind memory.
  • Media is not a limit at 300 users. Bursty CPU for thumbnails, idle disk, no errors.
  • Everything at once collapses, then recovers. 2,200 users across all six shapes: within a minute the thread pool queue passed 4,000, the server served one HTTP request a second, heartbeats timed out and 3,600 reconnects followed. Two minutes after the load stopped the server was idle again, same process, no restart.
  • A person feels the browser before the server. In a room with 20 to 30 messages a second the admin's tab needed seconds to post and a minute to see its own echo, while the server answered in under 100 ms and the synthetic users saw 75 ms.

Test machine

Server
Hetzner Cloud VPS, Helsinki. 4 vCPU AMD EPYC Milan (2 cores × 2 threads), 16 GB, no swap, 160 GB virtual SSD, KVM. The specs match the CCX23 plan; the plan name was not confirmed in the console.
Software
Ubuntu 26.04.1 LTS, kernel 7.0.0-30. .NET 10, ASP.NET Core 10.0.12. Yap built from main of 2026-10-16, a systemd service. SQLite 3.46.1. Caddy 2.6.2 for TLS, forwarding to Yap on 127.0.0.1:5221. Cloudflare proxy in front. ffmpeg 9.0.2, yt-dlp 2026.08.19, Deno 2.9.6.

Load machine

Method

A virtual user keeps one WebSocket, sends heartbeats on the browser's rhythm (10 s visible, 60 s hidden), and behaves by a preset: thinks, types, sends short and long texts, emoji, video links, generated JPEG uploads, replies, reactions and direct messages, with bursts, room hops, idle spells and hidden tabs. The orchestrator ramps the user count in steps and holds each step. Each message carries its send time in its client id, so the time from sender to any receiver is measured without clock sync.

Percentiles are the upper bound of a log-spaced bucket (75, 100, 150, 200, 300, 500, 750 ms, …), so a reported p95 of 150 ms means at most 150 ms. The server numbers come from GET /api/admin/load, one sample a second: CPU, memory, GC, thread pool queue, hub connections, messages and hub sends per second, request p95, writer queue depth and presence sweep time. The hub-sends counter counts calls, and a group send to a room is one call, so at 800 connected users the count is about 800 per message, nearly all of them the per-user unread events.

One room, many members

Every action in a room costs one hub send per connected member, so the work grows with the square of the room size. At 2,000 members in one room:

ActionSendsPath in the code
A message2,000ChatHubBroadcaster.ToChannel, one group send
Its unread count2,000 + 2,000 writesChatService.IncrementUnread: every connected user and every account with the room unmuted, including people who have the room open
Typing before it4,000PresenceService.SetTyping, on and off
A presence change2,000PresenceService.Changes.Raise, one event per change to everyone

In run 1 the idle crowd of 2,000 produced about two messages a second and three presence changes a second (hidden users coming back), about 20,000 hub sends a second and 15 to 20 MB/s outbound. At about 150 µs of CPU per send that is three cores, and Caddy paid once more for TLS on every frame. Run 6 shows the same slope with everyone active:

800 active users in one room cost 58 % on average and 70 % at peak, with no errors. The idle crowd looked worse at the same count because its cost was presence changes plus the writer, not messages.

The persistence writer

With persistence on, every room message queues one read-state write per account. The writer drains the whole queue in one transaction, and each write runs its own SaveChangesAsync on one shared DbContext. Each save checks every entity the context already tracks, and the context tracks every row touched so far in the batch. A batch of N writes costs about N² compares. A bigger backlog makes a bigger batch, a bigger batch makes each write slower, and the backlog grows further.

The depth grows by about 3,500 a second from the moment the plateau is reached, at the same rate in a quiet second with one message as in a busy one with sixteen: the writer is no longer draining. The working set grows with it, about 300 bytes per queued write. The clients see nothing, send-to-appear stays at 150 ms, because the unread counts are served from memory. On the VPS the database command rate fell from 14,000 a minute to 200 while one transaction kept running; nothing committed until the restart.

The limit is about 4,000 to 5,000 writes a second on this box. The dm-heavy run settles the reading: it lost the writer at 300 users with about a thousand TCP connections, where big-room with 400 users kept it, because the room message rates differed. After the dm-heavy run the database held everything up to 18:20:21, so the last three and a half minutes of the run were lost on disk.

The queue is unbounded, with a comment in PersistenceWriter that a chat this size never outruns SQLite. At 1,000 members in one room it does. The failure is silent for users and visible to the operator only as memory growth and as data missing after a restart.

Small rooms

Run 5 put 500 users in twenty rooms of 25. The hub sent 501 events per message: 25 for the message itself and about 475 unread events, one to every connected user whatever room they were in. The writer took one read-state write per account, 1,500 per message, and was lost at 7 messages a second. At 1,500 users the run looked like run 1 at 2,000 in one room: 27,000 to 30,000 hub sends a second, HTTP p95 at 5 seconds, 64 upload timeouts, a working set of 1.2 GB. Twenty rooms of 25 cost the same unread work as one room of 500. The only savings of small rooms are the message and typing sends.

Everything at once

Run 10 started six orchestrators together with persistence off: big-room 400, small-rooms 400, dm-heavy 400, media-heavy 200, burst 300, idle-crowd 500. 2,200 users, 60 s ramp, 3 min hold.

At 18:45, still in the ramp, the server was at 91 % CPU with 63 messages and 34,000 hub sends a second. A minute later the thread pool queue stood at 4,200, the server served one HTTP request a second, and the hub sends had fallen to 1,900 a second because the sends themselves waited in the same queue. The admin's browser showed an empty grey shell: the bootstrap request never came back, and a login took more than a minute. A minute after that the heartbeats timed out, connections dropped from 1,869 to 1,472, and the presence leave and join events of the reconnects pushed the hub sends to 42,800 a second. The orchestrators counted 3,862 errors and 3,600 reconnects in four minutes, with send-to-appear, HTTP and heartbeat round trips all at 30 seconds.

VPS peaks: 8,070 TCP connections (half of them Caddy to Yap), CPU at or above 95 % for 164 seconds, Yap at 3.9 of 4 cores, 96 seconds of stalls with almost no outgoing traffic, 46.9 MB/s in the bursts between them, 864 MB. Seven cancelled uploads in the log, no crash.

The server recovered on its own, the same process from start to end. The design degrades badly past its CPU but does not break: nothing leaked, no thread was stuck, the working set went back to where it was.

What a person sees

The admin kept a browser tab open next to the load. The orchestrator's numbers come from clients that only parse the JSON; a browser also has to render it.

  • At 1,000 idle users with persistence on: navigation laggy, own messages post after a few seconds, the typing indicator busy all the time, the page usable.
  • At 800 active users in one room: the lobby a firehose of 13 messages a second; switching to another room shows an empty room for a long time before the composer and history appear.
  • In the dm-heavy and burst runs, 20 to 33 messages a second: posting took seconds, navigation stopped, the own echo arrived after more than a minute, while the server answered requests in 20 to 44 ms at p95 and the synthetic users saw 75 ms. The echo arrived on its own after the run, without a reload, so the frames were buffered, not lost. A browser that cannot drain the stream lets the frames pile up, and its own echo waits at the end of that queue.
  • The side panel has no scrollbar with twenty rooms and 1,500 people in it. A hundred names in the typing indicator carry no information.

Possible changes, not applied

Recorded for a later decision. None are in the code.

Writer

  • db.ChangeTracker.Clear() after each save in the batch loop. Turns the cost of a batch from N² to N.
  • A fixed batch size, for example 500 writes per transaction, so one commit never waits on minutes of work and the disk stays close to memory.
  • Coalesce read-state writes inside a batch: the same (user, room) row is upserted once per message, and only the last value matters.
  • A bound on the queue, or a log warning when the depth passes a threshold, so a runaway shows before the working set does.

Fan-out

  • No unread event and no read-state write for a person who has the room open. In a big room that removes almost all unread traffic.
  • Typing events only below a room-size threshold, or one coalesced event per second per room.
  • Presence changes collected for about 500 ms and sent as one event with a list.

Deployment

  • Logging:LogLevel:Microsoft.EntityFrameworkCore.Database.Command set to Warning in production.
  • A host filter before yt-dlp. Every URL in a message starts a yt-dlp process today, including Wikipedia, GitHub and links to the server itself. YouTube failed every time from this VPS, which points at its IP being blocked.
